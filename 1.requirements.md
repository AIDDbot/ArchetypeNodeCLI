# Requirements Document

## Introduction

This feature involves creating a Node.js CLI archetype that serves as a structured template for building command-line interfaces using TypeScript. The archetype provides essential tools, configurations, and sample features to streamline CLI development while following modern Node.js best practices and avoiding deprecated dependencies.

## Requirements

### Requirement 1

**User Story:** As a developer, I want a TypeScript-based CLI archetype with modern Node.js features, so that I can quickly bootstrap new CLI projects with type safety and current best practices.

#### Acceptance Criteria

1. WHEN the archetype is created THEN it SHALL use TypeScript for all source code
2. WHEN the archetype is initialized THEN it SHALL be compatible with Node.js V24 LTS
3. WHEN dependencies are added THEN they SHALL be updatable to the latest versions
4. WHEN the project is built THEN it SHALL support running TypeScript files directly using `node --disable-warning=ExperimentalWarning main.ts`

### Requirement 2

**User Story:** As a developer, I want core infrastructure features built-in, so that I can focus on business logic rather than setup.

#### Acceptance Criteria

1. WHEN environment variables are needed THEN the system SHALL support loading from `.env` files using Node.js built-in `--env-file=.env`
2. WHEN logging is required THEN the system SHALL use integrated console logging for monitoring CLI operations
3. WHEN file changes occur THEN the system SHALL support watching using `node --watch` instead of nodemon
4. WHEN HTTP requests are needed THEN the system SHALL use Node.js built-in `fetch` instead of node-fetch

### Requirement 3

**User Story:** As a developer, I want sample business features included, so that I can understand how to implement CLI commands and extend the archetype.

#### Acceptance Criteria

1. WHEN the weather command is invoked THEN the system SHALL fetch and display weather information based on current IP geolocation
2. WHEN the help command is invoked THEN the system SHALL provide usage instructions and list available commands
3. WHEN IP geolocation is needed THEN the system SHALL use the IP Geolocation API (ip-api.com)
4. WHEN weather data is required THEN the system SHALL use the Open Meteo API

### Requirement 4

**User Story:** As a developer, I want proper tooling and code quality setup, so that I can maintain consistent code standards and catch issues early.

#### Acceptance Criteria

1. WHEN the project is created THEN it SHALL include ESLint configuration for linting and code quality checks
2. WHEN code is formatted THEN it SHALL use Prettier for consistent formatting
3. WHEN tests are written THEN they SHALL use Node.js built-in test runner (`node:test`) instead of Jest
4. WHEN assertions are needed THEN they SHALL use `node:assert/strict`

### Requirement 5

**User Story:** As a developer, I want essential runtime dependencies included, so that I can build feature-rich CLI applications with proven libraries.

#### Acceptance Criteria

1. WHEN terminal output needs styling THEN the system SHALL use Chalk for colorful output
2. WHEN building CLI interfaces THEN the system SHALL use Commander.js for command parsing and handling
3. WHEN data validation is required THEN the system SHALL use Zod for schema validation
4. WHEN dependencies are managed THEN the system SHALL NOT include deprecated packages (dotenv, jest, node-fetch, nodemon, tsc)

### Requirement 6

**User Story:** As a developer, I want comprehensive documentation and testing, so that I can understand, maintain, and extend the archetype effectively.

#### Acceptance Criteria

1. WHEN the project is created THEN it SHALL include a README with installation and execution instructions
2. WHEN documentation is needed THEN it SHALL include a docs folder with detailed development and usage information
3. WHEN code is written THEN public functions and classes SHALL have JSDoc comments
4. WHEN sample features are implemented THEN they SHALL have unit tests using Node.js built-in test runner
5. WHEN CLI commands are created THEN they SHALL have end-to-end tests
6. WHEN the project structure is defined THEN it SHALL follow organized folder structure for source code

### Requirement 7

**User Story:** As a developer, I want the archetype to be development-focused, so that it serves as a learning tool and starting point rather than a production application.

#### Acceptance Criteria

1. WHEN the archetype is used THEN it SHALL be clearly documented as a learning tool and starting point
2. WHEN the archetype is distributed THEN it SHALL include clear disclaimers about not being intended for production use
3. WHEN examples are provided THEN they SHALL serve as guides for creating custom CLI applications
4. WHEN the project is executed THEN it SHALL be designed to run only in development environments
