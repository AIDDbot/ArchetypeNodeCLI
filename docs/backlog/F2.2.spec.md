# F2.2 Provide `.env.example` and ignore `.env` Specification

Provide a tracked `.env.example` file with documented, safe placeholders and ensure real `.env` files are ignored by git, preventing accidental commits of secrets. Align example syntax with Node's `--env-file` semantics and keep defaults in code.

- **Epic**: E2 Configuration & Environment
- **Priority**: ‼️ Critical
- **Product Requirements**: 
  
- R2 Environment configuration

## User Story 1

- **As a** developer
- **I want to** have a `.env.example` with documented keys and safe defaults
- **So that** I can quickly create my local `.env` without guessing names or formats

### Acceptance Criteria

- [ ] The repository SHALL include a versioned `.env.example` file containing representative keys used by the CLI with placeholder values and brief comments.
- [ ] WHEN a new contributor clones the repo, the `.env.example` SHALL allow creating a working `.env` by copying and editing values.
- [ ] WHERE Node `--env-file` syntax applies, the example SHALL use compatible `KEY=VALUE` lines and allow comments with `#`.

## User Story 2

- **As a** maintainer
- **I want to** ensure `.env` files are not committed
- **So that** secrets and local overrides remain private

### Acceptance Criteria

- [ ] The repository SHALL ignore `.env` and common variants (e.g., `.env.local`, `.env.*.local`) via `.gitignore`.
- [ ] WHEN a developer runs `git status`, THEN any `.env*` files specified in ignore rules SHALL not appear as untracked.
- [ ] IF a `.env` exists locally, THEN Node’s `--env-file` or `--env-file-if-exists` usage from F2.1 SHALL be compatible with this setup.

> End of Feature Specification for F2.2, last updated 2025-08-20.
